## 1. What this project is
A **single-user, self-hosted web app** to store, browse, and add recipes. Recipes can be
added via a **structured form** or by **pasting free text** (TikTok / Instagram caption,
website text), which is normalised into one **standardised JSON recipe format**. Recipes
render with optional images, an optional source link, and **macros per portion and per
100 g**. Macros come from **Open Food Facts** (search-and-pick per ingredient) with an
**LLM-estimate** button and always-editable manual override.

The user is **German** and cooks from German recipes — this drove the nutrition-source
choice (see §3, Nutrition).

## 3. Locked design decisions (agreed with the user at GATE 0)
Full detail is in the plan's D1–D6. Summary:

- **Architecture:** split, monorepo. `/backend` (C++) + `/frontend` (Angular) + `/docs` +
  `docker-compose.yml`.
- **Backend:** **C++ with the Drogon framework** — chosen deliberately **to learn C++**
  (user accepts the extra plumbing). CMake + vcpkg; `drogon[postgres]` feature required;
  `valijson` for JSON-Schema validation; libcurl (sync) for HTTP to OFF and the LLM.
  DB access via Drogon `DbClient` `execSqlSync`.
- **Frontend:** **Angular SPA** (chosen to learn a structured framework; Reactive Forms
  suit the dynamic ingredient form). Pin the Angular major version. Dev proxy + prod
  nginx `/api` reverse-proxy → **same-origin, no CORS**.
- **Database:** **PostgreSQL** (chosen over SQLite because the user may add auth /
  multi-user **later**). Migrations = plain SQL files + idempotent runner with a
  `schema_migrations` table.
- **Auth:** schema is **auth-ready** (a `users` stub table + nullable `owner_id` on
  recipes) but **NO auth is implemented this phase**. User confirmed this default.
- **Interchange format:** **JSON** is canonical; the **JSON Schema in `docs/` is the
  single source of truth**, mirrored by the C++ struct + Angular type, validated at every
  boundary. Carries a **`schemaVersion`** field. (A YAML export/import convenience could
  layer on later; JSON stays canonical.) Storage is relational Postgres, not a JSON blob.
- **Nutrition:** **Open Food Facts (OFF)** behind a `NutritionSource` interface (USDA left
  as a future secondary-source seam). **Search-and-pick per ingredient** (human in the
  loop, not fuzzy auto-match). **Live OFF API on first lookup, then cached in Postgres**
  (`foods` table keyed by barcode `code`; `ingredients.food_id` links to it) so repeat
  lookups need no network. OFF API contract is pinned (endpoint, descriptive
  `User-Agent`, 429/backoff). Per-100 g mapping pinned: `energy-kcal_100g` (else
  `energy_100g ÷ 4.184` — this avoids a kJ/kcal ~4.18× calorie bug), plus
  proteins/carbohydrates/fat `_100g`; products missing `*_100g` are not-pickable/flagged.
  ODbL licence (fine for personal use; a small attribution line shown in UI).
- **Macros:** stored per-serving + servings + total weight; **per-100 g is derived**
  (`perServing × servings ÷ totalWeightG × 100`). Shows **"—"** whenever weight is
  incomplete (any ingredient unpicked or any unit unresolved). Sources: OFF / LLM / manual,
  always overridable.
- **Paste parsing:** two engines behind a `RecipeParser` interface — `RuleBasedParser`
  (offline) and `LlmParser` (local LLM). User selects the engine; parsed result always
  shown in an **editable preview** before saving.
- **Local LLM:** OpenAI-compatible endpoint (Ollama). Env: `LLM_BASE_URL` (default
  `http://localhost:11434`), `LLM_MODEL`, optional `LLM_API_KEY`; client appends
  `/v1/chat/completions`. Off unless the engine toggle selects it. Output validated
  against the schema with fallback.

   - **Steps** are flat/ordered and may be empty (video-only captions). Caption-provided
     macros fold into `macroSource: "manual"` (vetted in the editable preview).

   (multi-select, AND); **favorites-only** toggle; macro filters **`minProtein` +
   `maxCalories`**; sort by newest (default) / title / highest-protein. Full-text over
   ingredients/steps deferred (needs Postgres FTS).
3. **Paste parser depth — LOCKED** (plan D4 + T3.1): rule-based parser is the
   **best-effort primary** engine (fully handles the pinned caption patterns, works
   offline); `LlmParser` is the **fallback** for messy captions. **Scope this phase =
   social captions only** (TikTok/Instagram). Pasted website text and URL/HTML
   (schema.org JSON-LD) are **out of scope** — a clean later addition behind the same
   `RecipeParser` interface.
4. **LLM specifics — LOCKED** (plan D3): **no translation** — LLM parses captions into
   schema JSON preserving the original language (German stays German); OFF search handles
   German terms. Model is **not hard-coded** — `LLM_MODEL` picks it at runtime, so
   switching is an env change + restart (model must be pulled in Ollama), no rebuild.
   Documented **reference default `qwen3.5-9b`** (fast, best-family German), quality
   option **`qwen3.8-27b`**, and **Gemma 4 27B (Q4_K_M)** noted as a JSON-adherence
   alternative. JSON reliability comes from structured-output mode + `valijson` + fallback,
   not model obedience. (User runs Qwen locally; confirmed 2026 web check.)

5. **Milestone ordering / thin-slice — LOCKED:** keep the M1→M6 order as written; deploy
   last. No reorder. Rationale: M1+M2 already form the first end-to-end vertical slice
